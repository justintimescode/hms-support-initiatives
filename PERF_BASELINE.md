### Where boot time goes (instrumented fetch/parse timeline, ms from navigation)

```
  446 →  6206   5760ms  fetch /api/cache/jira        ← 400 MB
  449 →  2351   1902ms  fetch /api/cache/jira        ← 400 MB, SECOND request
 1772 →  6206   4434ms  fetch /api/cache/sn          ← 1 KB, starved behind the two above
 2351 →  6207   3856ms  json() /api/cache/jira       ← JSON.parse ~400 MB
 6206 → 10586   4380ms  json() /api/cache/jira       ← JSON.parse ~400 MB, again
 6206 → 10194   3988ms  json() /api/cache/sn
10194 → 10587    393ms  fetch .../source (xlsx #1)
12154 → 12177     23ms  fetch .../source (xlsx #2)

long tasks > 100ms:  754ms @6207 · 310ms @10276 · 237ms @10782 · 212ms @12206 · 2536ms @13376
```

Two facts here matter most:

1. **The 400 MB Jira cache is fetched and JSON-parsed twice.** The single
   `loadCache()` call site is the mount effect in
   [useAppData.js](src/lib/useAppData.js#L361-L386); `StrictMode` double-invokes
   mount effects, so in dev it runs twice. Even one pass is ~5.8 s of transfer +
   ~3.9 s of parse. `loadCache` has no in-flight dedupe and no memoization
   ([jira-client.js](src/lib/jira-client.js#L384-L396)).
2. **The 2,536 ms long task at ~13.4 s** is `cached.issues.map(enrichIssue)` —
   11,098 issues, each walking its full changelog
   ([jira-enrich.js](src/lib/jira-enrich.js#L155)). `enrichIssue` also keeps the
   raw `changelog` array on every output object
   ([jira-enrich.js](src/lib/jira-enrich.js#L78)), which is why the heap lands in
   the hundreds of MB.

This is the most important measurement in the whole baseline: **the aggregation

## 5. Visual jank walkthrough (manual, verified with a scripted content timeline)

1. **Boot shows the wrong empty state for ~10 seconds.** From ~1.5 s to ~11 s
   after navigation the Dashboard renders
   *"Welcome — load some data to begin"* — the no-data empty state — and only
   then flips to the real dashboard. Captured timeline:

   ```
   t=  1572ms  titles: Dashboard / "Welcome — load some data to begin"
   t=  8091ms  titles: Dashboard / "Welcome — load some data to begin"
   t= 11342ms  titles: Dashboard / 951 / 68.1% / 6.7h / 85 / Connections / Jump to
   ```

   Cause: pages branch on `rows == null` ([Home.jsx](src/pages/Home.jsx#L36))
   and there is no "still loading" state between "no data" and "data". The
   `restoringCount` banner that *would* explain it is rendered only inside
   [ImportsCard.jsx](src/components/connections/ImportsCard.jsx#L106) on the
   Connections page.
2. **No layout shift measured on tab switches** — the shell is fixed-width and
   chart containers have explicit `height` values.
3. **The shell does not remount between sibling routes** — confirmed by the
   render log: `Router×1, Shell×1, TopBar×1` re-render, `Mount`/`Unmount`
   entries are limited to the page subtree.
4. **`Cases` and `Jira Statistics` clicks feel like a stall** — 364 ms / 339 ms
   with 139 ms / 232 ms of that main-thread-blocked, so the click is
   acknowledged late and there is no intermediate state.
5. **Every page mount plays a 0.32 s `fade-in`** ([Shell.jsx](src/components/layout/Shell.jsx#L85),
   applied by [Section.jsx](src/components/layout/Section.jsx#L5)) and
   `.hoverlift` animates `transform`/`box-shadow`. Neither is gated behind
   `prefers-reduced-motion`; the existing reduced-motion block in
   [index.css](src/index.css#L282-L296) only covers the theme toggle.

## 8. What I could not measure, and why

- **Lighthouse / Web Vitals** — the app is a local-first tool; the production
  build has no dev server, so it has no Jira proxy and no `/api/cache/*`, i.e.
  no data. A Lighthouse score against an empty-state prod build would measure
  nothing real. Boot timings above are therefore taken against the dev server,
  which is also the only mode where the Jira cache and disk mirror exist.
- **Dev-mode overhead** — all runtime numbers are dev-build numbers
  (unminified React, per-render performance-track instrumentation). Absolute ms
  will be lower in the packaged Electron app; before/after comparisons within
  the same mode are still valid, and every later phase will re-run the identical
  script.
- **The second 400 MB fetch is dev-only.** It comes from `StrictMode`
  double-invoking effects. The first fetch + parse (~9.7 s combined) is real in
  production too.
- **Electron main-process startup** — out of scope for this pass; the browser
  boot path is the same code.

## 9. Prioritized bottleneck list

Ordered by measured cost. Each is tagged with the phase it belongs to and cites
the code it came from.

### P1 — Jira cache load: ~9.7 s and ~400 MB of the boot, twice in dev · *data-layer*
`loadCache()` fetches a 390 MB JSON file and `JSON.parse`s it on the main
thread, then `enrichIssue` maps 11,098 issues (2,536 ms long task) and keeps
each issue's full `changelog` in the result. Evidence: §3 timeline; heap
578–1020 MB. Code: [jira-client.js#L384](src/lib/jira-client.js#L384),
[useAppData.js#L361](src/lib/useAppData.js#L361),
[jira-enrich.js#L78](src/lib/jira-enrich.js#L78).
No in-flight dedupe on `loadCache`, so concurrent callers each pay full price.

### P2 — 1,096 kB initial chunk with zero route splitting · *bundle/code-split*
All 24 pages + all 18 chart blocks + recharts' 350 KiB cone + dompurify +
papaparse ship before the first pixel. Evidence: §2 attribution; cold≈warm nav
times in §4 prove nothing is deferred. Code:
[App.jsx#L3-L26](src/App.jsx#L3-L26).

### P3 — 10 seconds of "Welcome — load some data to begin" during boot · *perceived-smoothness*
The app shows its *no-data* state while data is loading, then snaps to a full
dashboard. Evidence: §5.1 timeline. Code:
[Home.jsx#L36](src/pages/Home.jsx#L36), and `restoringCount` is only surfaced on
Connections ([ImportsCard.jsx#L106](src/components/connections/ImportsCard.jsx#L106)).

### P4 — `enrichRow` × 951 = 664 ms and xlsx parse = 733 ms, both on the main thread · *data-layer*
Every import is parsed and enriched on the UI thread — twice over on a cold
restore (2 imports), and again per import activation. Evidence: §3 bench. Code:
[useAppData.js#L667](src/lib/useAppData.js#L667) (`enrichedAll` memo),
[useAppData.js#L155](src/lib/useAppData.js#L155) (`parseFileToRows`). The worker
already does the same enrichment for SQL ([db.worker.js#L14](src/workers/db.worker.js#L14)),
so the row data is enriched twice per import by two different code paths.

### P5 — Cases table builds 951 × 8 cells on every mount and sort · *render*
364 ms mount / 227 ms sort / ~139 ms blocked, with only 73 component renders —
the cost is DOM + inline style object churn, not component count. Search filters
on every keystroke over the full list.
Evidence: §4. Code: [CaseTable.jsx#L105](src/components/CaseTable.jsx#L105),
[CaseTable.jsx#L61](src/components/CaseTable.jsx#L61).
Scroll is already smooth (§4), so this is a mount/sort problem, not a
virtualization-for-scroll problem.

### P6 — Unmemoized `flatMap` in page bodies invalidates child memos every render · *render*
[CasesPage.jsx#L9](src/pages/CasesPage.jsx#L9) and
[JiraBlockersPage.jsx#L11-L16](src/pages/JiraBlockersPage.jsx#L11-L16) build a
fresh array on every render outside `useMemo`, so `CaseTable`'s `sorted` memo and
`JiraDashboard`'s four memos (`summary`, `tableRows`, `sorted`, `ticketGroups`)
recompute on every parent render — including renders triggered by an unrelated
sidebar/filter change.

### P7 — `JiraDashboard` defines components during render · *render*
12 `react-hooks/static-components` lint errors: `Field` is declared inside
`JiraCaseDetail` ([JiraDashboard.jsx#L71](src/components/jira/JiraDashboard.jsx#L71)),
forcing unmount/remount of all 12 field subtrees per render. Plus 3
`react-hooks/purity` errors from `Date.now()` calls in render paths
([#L62](src/components/jira/JiraDashboard.jsx#L62), [#L66](src/components/jira/JiraDashboard.jsx#L66),
[#L220](src/components/jira/JiraDashboard.jsx#L220)).

### P8 — Charts re-render on unrelated state changes · *render*
`useAppData` returns a **fresh object literal** every render
([useAppData.js#L889](src/lib/useAppData.js#L889)) into
`<Outlet context={appData} />`, so every `useOutletContext()` consumer re-renders
whenever `AppLayout` re-renders — which includes any filter change and any
background Jira sync tick. On chart-heavy pages that is 250–1,100 Recharts
component renders (§4). Note `jiraAutoSyncing` is already deliberately kept
separate for this reason ([useAppData.js#L222](src/lib/useAppData.js#L222)) —
the pattern just isn't applied to the context object itself.

### P9 — `teamMembers` computes 7 aggregations × every analyst regardless of page · *data-layer (low value)*
[useAppData.js#L723](src/lib/useAppData.js#L723). Measured at **3 ms** for 951
rows / 14 analysts — recorded for completeness, **not worth optimizing** at this
data size. Only worth revisiting if row counts grow by an order of magnitude.

### P10 — `.fade-in` / `.hoverlift` ignore `prefers-reduced-motion` · *perceived-smoothness / a11y*
[Shell.jsx#L85](src/components/layout/Shell.jsx#L85),
[Shell.jsx#L41](src/components/layout/Shell.jsx#L41); the existing
reduced-motion block ([index.css#L282](src/index.css#L282)) covers only the
theme toggle.

### Explicitly *not* a bottleneck (measured, leave alone)

- **Scroll performance** — 0 dropped frames on both long pages (§4).
- **Aggregation math** — 5 ms total (§3). No memoization work needed.
- **Duplicate dependency versions** — one real case (`immer` ×2, ~8 KiB
  combined, §2). Worth an `overrides` entry in Phase 2, not worth a refactor.
- **exceljs** — already lazy; 930 kB never loads unless an xlsx is parsed.
- **Shell remounting** — already correct; shell re-renders but does not remount.

## 10. Proposed adjustment to the phase plan

Based on the above, the generic plan's ordering is wrong for this codebase and I
propose reordering. Phase 1 as written ("route/tab switching & bundle size") is
P2 — real, but it is not what makes the app feel slow; the boot path is.
Recommended order:

1. **Phase 1 — boot path (P1, P3, P4).** Dedupe/short-circuit the Jira cache
   load, get the 400 MB parse and the 664 ms enrichment off the critical path
   (with byte-identical outputs proven by the §3 digests), and replace the
   wrong-empty-state with a real loading state. Biggest measured win by an order
   of magnitude.
2. **Phase 2 — bundle & route splitting (P2).** `React.lazy` per route, recharts
   + dompurify + papaparse out of the initial chunk.
3. **Phase 3 — render hot spots (P5, P6, P7, P8).** Memoize the page-body
   `flatMap`s, hoist `Field`, stabilize the Outlet context object, and cut the
   Cases table's mount/sort cost.
4. **Phase 4 — perceived smoothness (P3 follow-through, P10).** Loading states
   at every async boundary, reduced-motion gating.
